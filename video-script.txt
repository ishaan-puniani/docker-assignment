NOTES ON KUBERNETES - VIDEO SCRIPT
Target length: about 9 minutes (allowed: 5-10 minutes)

How to read this script:
  [SHOW]  = what to have on screen / what to do
  SAY:    = what to say (rephrase in your own words; don't read word for word)
  $       = command to type in the terminal

APP_URL below means:
  - Docker Desktop:            http://localhost:30080
  - DigitalOcean Droplet:      http://<droplet-ip>:30080
  - Codespaces / minikube:     the port-forward URL for port 8080
                               (run: kubectl port-forward svc/web 8080:80)
  For curl in Codespaces/minikube use http://localhost:8080 instead of :30080.

Commands are written for a bash terminal (Codespaces, Droplet, Git Bash).
In Windows PowerShell, write curl.exe instead of curl, and for the POST:
  curl.exe -X POST -H "Content-Type: application/json" -d '{\"text\":\"added with curl\"}' http://localhost:30080/api/notes

2. WHAT THE PROJECT IS ABOUT                          0:30 - 1:15
======================================================================
[SHOW] README section "What it does".

SAY:
"The application is a shared notes board. Users open a web page, add short
notes of up to 500 characters, see all notes, and delete them. The footer
shows the number of notes, their average length, and which pods served the
request.

The app is deliberately small and doesn't really need to scale. To make the
design make sense, imagine a company-wide notice board used by thousands of
employees, with far more reads than writes. Then you'd want to scale the
web tier and the data tier separately, which is exactly what this
architecture allows."

3. ARCHITECTURE AND THE MICROSERVICES                 1:15 - 2:45
======================================================================
[SHOW] Architecture diagram (README or docs/2-architecture-design.pdf).

SAY:
"The system has three parts, each running as its own Kubernetes Deployment
behind its own Service.

First, 'web'. It's a Node.js Express service I wrote. It serves the web page
and has its own REST API under /api. It holds no data. When the browser asks
for notes, web calls the notes-api service over REST and returns the answer.
It also calculates the statistics. This is where I programmatically consume
a REST API."

[SHOW] web/server.js - point at the callApi function and the /api/stats route.

SAY:
"Here you can see callApi, which uses fetch with a 3-second timeout. If
notes-api doesn't answer, web returns a 503 instead of hanging.

Second, 'notes-api'. This is the REST API I built for the notes data. It has
GET and POST on /notes and DELETE on /notes/{id}. It validates the input and
is the only service that talks to the database."

[SHOW] notes-api/server.js - point at the POST /notes route and its validation.

SAY:
"Third, MongoDB, the database. It's the official mongo image, the only
container I didn't write. It stores its data on a persistent volume, so the
notes survive restarts.

Only web is reachable from outside the cluster. notes-api and MongoDB are
internal only."

8. SCALING AND PERSISTENCE                            6:05 - 7:05
======================================================================
SAY: "Each microservice scales independently. Let's scale only notes-api to four."

$ kubectl scale deployment notes-api --replicas=4
$ kubectl get pods

SAY:
"notes-api now has four pods and web still has two. I could do the same
for web without touching notes-api."

SAY: "Now persistence. I'll delete the database pod."

$ kubectl delete pod -l app=mongo
$ kubectl get pods -w
   (wait for the new mongo pod to be Running, then Ctrl+C)

[SHOW] Refresh the browser.

SAY:
"Kubernetes created a new mongo pod, and all the notes are still there,
because the data lives on the persistent volume, not in the container."

$ kubectl scale deployment notes-api --replicas=2     (optional: reset)


======================================================================
9. WALK THROUGH THE KUBERNETES YAML                   7:05 - 8:35
======================================================================
[SHOW] Editor with k8s/app.yaml. Scroll down as you talk.

SAY:
"Finally, the Kubernetes file. Everything is in one manifest, app.yaml.

- At the top is a Secret with the MongoDB username and password. In a real
  project I wouldn't commit this. I'd use Sealed Secrets or a cloud
  secret manager.

- Then a PersistentVolumeClaim of 1 gigabyte for the database.

- The mongo Deployment has one replica and uses the Recreate strategy, so two
  database pods never write to the same volume. It takes its credentials from
  the Secret and mounts the volume at /data/db.

- The mongo Service is ClusterIP, so it's internal only.

- The notes-api Deployment has two replicas. It builds its MONGO_URL from the
  Secret values. It has a readiness probe on /health, so Kubernetes only
  sends traffic when the pod is ready, and it has CPU and memory requests and
  limits.

- The notes-api Service is also ClusterIP.

- The web Deployment is similar: two replicas, the same probe and limits, and
  NOTES_API_URL pointing at http://notes-api:5000. That's Kubernetes DNS
  service discovery.

- And the last object, the web Service, is a NodePort on 30080. It's the
  only way into the application from outside."

10. SECURITY AND WRAP-UP                              8:35 - 9:15
======================================================================
[SHOW] README / docs security section (optional).

SAY:
"On security: only web is exposed, the database requires a password that
comes from a Secret, input is validated, the page can't be used for script
injection, and the containers run as a non-root user with resource limits.
What's still missing for production is user login, HTTPS, network policies
between services, and proper secret management. These are described with
their fixes in the documentation.

To summarise: two microservices I built, both with REST APIs, one calling
the other, plus MongoDB with persistent storage, deployed with Kubernetes
and reachable from the browser. Thanks for watching."
